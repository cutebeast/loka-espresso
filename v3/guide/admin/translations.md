# Admin Portal: Translations

## Pages
- `/translations/pwa` — Customer PWA
- `/translations/admin` — Admin Portal
- `/translations/staff` — Staff Portal

`/translations` redirects to the Customer PWA page. In the sidebar, **Translations** is an expandable item with these three pages.

## Purpose
Manage the **interface text** of the three apps across all supported locales. English (`en`) is the source language; each page edits the the target locale (zh):

| Locale | Language |
|--------|----------|
| `zh` | Chinese |

Each page is backed by its own translation namespace:

| Page | Namespace | Covers |
|------|-----------|--------|
| Customer PWA | `pwa-ui` | Every label, button, and message in the customer app. |
| Admin Portal | `admin-ui` | This portal's own interface text. |
| Staff Portal | `staff-ui` | The POS / staff app interface text. |

> These three pages cover **UI text only**. Content translations — menu items, events, help articles, promo banners, bundle products, survey questions — are auto-translated when the record is saved and are managed on their own pages' translation panels, not here.

## Where the keys come from

- English source keys are seeded into the database when a feature ships — you never create keys by hand.
- The pages derive their sections from the keys themselves, so newly shipped sections (e.g. a new `luckyDraw` group) appear automatically.
- If a page looks empty, no keys have been seeded for that namespace yet.

## Page layout

All three pages work the same way; only the text catalog differs:

- **Left sidebar** — translation keys grouped by section (the prefix before the first dot, e.g. `common`, `checkin`, `luckyDraw`). New sections appear automatically when new keys are added.
- **Translation grid** — one row per key: the key, the English source text, and one editable cell per locale.
- **Search box** — filters keys within the current section.
- Cells that already hold a translation have a solid border; empty cells are dashed and highlighted, so gaps are easy to spot.
- A key count under the grid shows how many keys the open section contains.

The grid shows one row per key even if some locales have no row for it yet — saving an empty locale's cell creates the record on the spot.

## Edit a translation

1. Open the page for the app you want to change.
2. Pick a section in the left sidebar (or search for the key).
3. Click the cell for the target locale and type the translation.
4. The cell saves when you click away or press Enter — a confirmation appears briefly.

Manual edits are protected: saving a cell marks that row as manually edited (`is_auto_translated = false`). The scheduled AI review only re-checks auto-translated rows, so **your manual corrections are never overwritten** by the weekly review.

## Auto-translate (DeepSeek)

Two levels of batch translation, both filling **missing** translations only — existing text (manual or machine) is never overwritten:

- **Translate All (top bar)** — per-locale buttons that translate every missing key across all sections for that locale. A progress counter (`done / total`) shows while it runs.
- **Section buttons** — per-locale buttons in the open section's header that translate only that section's missing keys.

Translations are generated by DeepSeek with F&B context; brand names (Loka, Bloom, Origin, Reserve) and Turkish dish names are intentionally kept untranslated. The API key and model are configured under **Marketing → Campaign Settings**.

## Placeholder syntax

Some strings contain placeholders that the app fills at runtime. Keep them verbatim in every locale — the syntax differs per app:

| App | Placeholder syntax | Example |
|-----|--------------------|---------|
| Admin Portal | Double braces | `{{name}}` |
| Customer PWA | Single braces | `{points}` |
| Staff Portal | Single braces | `{seconds}` |

A translated string whose placeholder syntax is wrong shows up in the app as literal `{name}` / `{{name}}` text — check this first when a string looks broken.

Example — the PWA key `checkin.pointsEarned` has the English source `+{points} points earned`; every locale must keep `{points}` exactly as-is.

## Sync to JSON (Customer PWA page only)

The Customer PWA page has an extra **Sync to JSON** button in the header. It:

1. Writes all `pwa-ui` translations from the database to the PWA's static Chinese locale file (`zh.json`). English is skipped — `en.json` is the hand-maintained source baseline.
2. Bumps the PWA build timestamp so devices detect a new version. This matters because the PWA caches translations in the browser for 24 hours — the version bump forces every device to pick up the new text instead of waiting out the cache.
3. Rebuilds the Customer PWA and restarts it.

The result message shows how many keys were written per locale (e.g. `zh: 812 keys`). Run it after editing PWA translations; otherwise the changes go live only at the next scheduled sync.

The Admin Portal and Staff Portal pages have no sync button — they read their translations from the database directly.

## Content translations (managed elsewhere)

Saving a content record anywhere in the portal auto-translates its customer-facing text into zh. This applies to:

- Menu items, categories, and bundle products
- Promo banners, vouchers, and rewards
- Events, info cards, product cards, and splash screens
- Surveys and their answer options
- Help articles and system pages
- Stores and inventory items
- Notification templates and campaigns

To correct one of these translations, open the record on its own page and use its translation panel — the same manual-edit protection applies there. If a brand-new record shows English everywhere, its translations either failed or are waiting for the nightly content-fill job (04:23).

## Scheduled translation jobs

These run automatically on the server; no action is needed unless you want changes live sooner.

| Schedule | Job |
|----------|-----|
| Sundays 03:17 | Weekly AI review of auto-translated **menu** translations. Manual edits are never touched. |
| Daily 04:23 | Content fill — translates newly added content records (menu, events, banners, etc.) that have no translations yet. |
| 1st of month 04:47 | AI review of the Admin Portal UI text (`admin-ui` namespace). |
| Sundays 05:41 | Automatic Sync to JSON (database → PWA locale files), running right after the weekly review so reviewed text reaches devices the same morning. |

## Suggested workflow

1. **After a feature release** — new keys appear in the relevant page's sections. Run Translate All for each locale.
2. **Review section by section** — read the machine output for the screens customers touch most, and fix anything off by editing the cell. Your fixes are protected from future AI reviews.
3. **Sync the PWA** — click Sync to JSON on the Customer PWA page so devices pick the text up immediately.
4. **Let the crons do the rest** — the weekly and monthly reviews keep improving auto-translated rows in the background.

## Tips

- Keep the English source accurate — every translation is generated from it. Fix the source first, then re-translate.
- After a feature release adds new keys, run **Translate All** per locale, then spot-check the important screens (checkout, loyalty, lucky draw).
- After editing PWA text, click **Sync to JSON** — don't wait for Sunday.
- Review machine translations for tone before big campaigns; anything you fix by hand stays fixed (see "Manual edits are protected").

## Troubleshooting

**A new key shows English in every locale.**
Run the section's auto-translate button, or Translate All for that locale. UI keys are only filled from these pages — the nightly content-fill job covers content records, not UI text.

**My edit was still visible in English in the PWA the next day.**
You edited the database but never synced — click **Sync to JSON** on the Customer PWA page and confirm the result message lists your key counts.

**A placeholder appears as literal text in the app.**
The placeholder syntax was changed in translation — restore the exact placeholder from the English source (see the syntax table above).

**Translate All finishes but some cells are still empty.**
Only keys with an English source text can be machine-translated; rows without source text are skipped. Fill in or fix the source first, then re-run.

**The Admin Portal itself shows the wrong language.**
Use the language selector in the portal header — the Admin Portal page edits the `admin-ui` text, it does not switch your viewing locale.

## Syncing Translations

Use the sync script to push EN baseline keys to the database:
```
sync_translations_to_json.py
```
This reads `customer-pwa/src/locales/en.json` and writes translations to the DB. The cron job picks up new EN keys and fills zh translations automatically.
